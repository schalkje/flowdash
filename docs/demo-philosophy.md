# Demo Philosophy

Demos are first-class artifacts in this repo, not throwaway scratchpads. They serve three audiences simultaneously, and any one demo should answer all three:

1. **Library evaluators** — "What does this thing actually look like? Show me, fast."
2. **Contributors learning the codebase** — "Where's a minimal example of this feature in isolation?"
3. **The test suite** — Playwright drives the same HTML pages a human would browse. If a demo breaks, a test breaks.

This document captures the conventions that make all three audiences happy.

## Five conventions

### 1. One feature per page (at the small end)

The numbering progression goes:

- **`01_*` … `09_*`** — single node types in increasing complexity (basic → rect → circle → lane → columns → adapter → foundation → mart → group).
- **`10_*`** — edges (cross-cutting; binds nodes together).
- **`11_*`** — full integrated dashboard / showcase.
- **`12_*` … `17_*`** — feature-cross-cutting demos (selection, zoom, status, minimap, overlay, prerender) that don't fit cleanly into a node-type bucket.
- Future ranges should follow the same logic — pick a number that semantically slots in.

A page near the small end of the progression should isolate **exactly one** concept. Don't show three node types on the "rectangular node" page.

This makes every page useful as a regression target: when the lane demo breaks, you know it's the lane code.

### 2. Static, inline data

All fixture data lives next to the page, typically in `js/graphData.js` or as inline `<script>`. Never `fetch()` JSON for demo data — demos must work over `file://` and survive being checked into git.

The one acceptable exception is a demo that *demonstrates fetching* (planned: `18_data-loading/`). Make that one obvious.

### 3. Shared chrome, owned content

Use [`/dashboard/flowdash-demo.css`](../dashboard/flowdash-demo.css) for the demo header / control bar / info footer. This gives all demos a consistent shell so users can move between them without retraining their eyes.

The content area inside the chrome is yours to design.

### 4. Discoverable from the navigator

Every demo must be reachable from [`/index.html`](../index.html), the root sidebar navigator. The navigator is generated by `generateIndex.ps1`; on non-Windows machines, hand-edit it after adding a demo. (A cross-platform regenerator is on the roadmap.)

If a demo is *not* listed in the navigator, it doesn't exist as far as users are concerned.

### 5. Test-driveable

Demos serve double duty as test fixtures. Two requirements:

- **Stable selectors.** If a Playwright spec needs to find a control or a node, it should be able to use a class or id that won't change for stylistic reasons.
- **Settles deterministically.** Animations and async layout passes should reach a steady state quickly. The dashboard sets `data-flowdash-ready="true"` on its root once init resolves; demo pages that drive `Dashboard` directly should benefit automatically.

## Where each demo flavor belongs

| Folder | Audience | Style |
|--------|----------|-------|
| `01_*` … `11_*` | Library users + contributors + tests | Polished, narrow scope, navigator-listed, test-targeted |
| `d3_basics/` | New contributors learning D3 | Educational, can use third-party D3 examples; not test-driven |
| `experiments/` | Author's WIP ideas | Scratchpad. Older style is acceptable. May graduate into a numbered folder once stable. |

## Anti-patterns

- **Multi-feature demos.** "I'll show edges and groups together" — split them. Composed scenarios belong in `11_dashboard/` (the flagship), not in single-feature folders.
- **Hidden controls.** A demo control that requires the user to read the source to discover. Use visible buttons and labels.
- **Overlapping demos with no differentiation.** If two pages demonstrate the same thing, delete one.
- **Decorative debug logging.** `console.log` lines that aren't asserted on are noise. Remove them before merging.
- **Reaching into library internals.** A demo should use the same public API an external consumer would use (`createAndInitDashboard`, settings, `dashboard.main.root.onClick`, etc.). If you need a private hook, that's a sign the public API is missing something — file an issue.

## Adding a new demo: a checklist

```
[ ] Picked the smallest scope folder it belongs in (or proposed a new numbered folder).
[ ] Named the file descriptively (`auto-size-large.html`, not `test3.html`).
[ ] Used `flowdash-demo.css` for the header/footer chrome.
[ ] Inlined the data — no fetch().
[ ] Added an in-page description of what's demonstrated.
[ ] Verified the page renders cleanly in the browser at http://localhost:8000/<path>.
[ ] Registered in /index.html (re-ran generateIndex.ps1 or hand-edited).
[ ] Added a sibling README.md if the demo is non-trivial.
[ ] Added a Playwright spec if the demo exercises a new behavior.
[ ] Verified the demo works on both Chromium and WebKit (`npm test`).
```

## Quality bar for the flagship showcase

`11_dashboard/` is the page someone will see if they ask "what does FlowDash actually do?" It carries a higher bar than feature-isolated demos:

- All node types represented.
- Edges with multiple flow directions.
- A real-feeling dataset (e.g. `dwh-6.fixed.json`).
- A theme toggle.
- Minimap visible.
- Status legend.
- Selection / zoom interactions discoverable.

It is also the headline target for visual regression and performance benchmarks. That doubles the cost of changing it casually — flag major showcase changes in PRs explicitly.
