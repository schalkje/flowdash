# Current State Analysis

A candid map of what's working and what isn't, organized by the three primary goals from [`project-goals.md`](./project-goals.md). Every claim cites a file path or count so the assessment is verifiable and stays grounded.

> Snapshot date: 2026-05-04. Counts may drift; re-verify before relying on a specific number.

---

## Goal 1 — Reusable D3 library

### Strengths

- **Clear module boundaries.** [`dashboard/js/`](../dashboard/js/) holds 31 ES-module files with role separation: nodes (`nodeBase.js`, `nodeBaseContainer.js`, `nodeAdapter.js`, `nodeRect.js`, `nodeLane.js`, `nodeColumns.js`, `nodeFoundation.js`, `nodeMart.js`, `nodeCircle.js`), managers (`configManager.js`, `themeManager.js`, `layoutManager.js`, `zoomManager.js`, `statusManager.js`, `eventManager.js`, `geometryManager.js`), rendering (`edge.js`, `edgeBase.js`, `markers.js`, `minimap.js`), simulation (`simulation.js`, `forceBoundary.js`, `forceRectCollide.js`), zones (`zones/` subfolder).
- **Single public entry point.** [`dashboard/js/index.js`](../dashboard/js/index.js) re-exports the `Dashboard` controller and helpers; in browsers attaches to `window.flowDashboard`.
- **Production bundle.** [`dashboard/webpack.config.cjs`](../dashboard/webpack.config.cjs) externalises D3, outputs minified `flowdash.min.js` (~196 KB) plus CSS.
- **Versioning discipline.** `dashboard/package.json` carries `"prebuild": "npm version patch --no-git-tag-version"`, so every successful build bumps the patch version automatically. Currently at **v1.2.32**.
- **Standalone "drop-in" form.** [`dashboard/flowdash-bundle.html`](../dashboard/flowdash-bundle.html) ships a self-contained demo for instant evaluation.
- **Distribution scripts.** [`scripts/distribute.ps1`](../scripts/distribute.ps1), [`scripts/copy-flowdash-css.ps1`](../scripts/copy-flowdash-css.ps1), [`scripts/validate-dashboard-json.ps1`](../scripts/validate-dashboard-json.ps1).
- **Deep architecture docs.** [`/dashboard/documentation/`](../dashboard/documentation/) holds 24 markdowns including subsystem deep-dives (`implementation-nodes.md` ~25 KB, `zone-system.md`, `state.md`, `pre-render.md`, `minimap.md`, `auto-zoom-behavior.md`, `settings.md`).

### Gaps

- **Version drift between packages.** Root [`package.json`](../package.json) is at `v1.0.0` (test harness only). [`dashboard/package.json`](../dashboard/package.json) is at `v1.2.32`. The dual-package model is not documented; an outsider can't tell which version is "the library."
- **Root build script is misleading.** Root `package.json` defines `"build": "webpack --mode production"`, but there is no `webpack.config.cjs` at the repo root. The real build lives at [`dashboard/webpack.config.cjs`](../dashboard/webpack.config.cjs).
- **README references a missing file.** [`README.md`](../README.md) points to `TEST_PLAN.md` multiple times; that file does not exist in the repo. Real testing strategy docs live at [`dashboard/tests/TESTING_STRATEGY.md`](../dashboard/tests/TESTING_STRATEGY.md) and [`tests/COMPREHENSIVE_TESTING.md`](../tests/COMPREHENSIVE_TESTING.md).
- **No release / versioning policy.** No doc explains when to run `build` vs `build:analyze`, how to publish, what triggers a minor or major bump, or how external apps should pin their dependency.
- **No contribution guide.** "How do I add a new node type?" requires reading source. (The closest pointer is [`dashboard/documentation/implementation-nodes.md`](../dashboard/documentation/implementation-nodes.md), which is reference material, not a how-to.)
- **No npm publication.** The package is not on npm; consumers must vendor the bundle or check the repo out. This is a fine choice but should be a stated, intentional one.

## Goal 2 — Interactive demos

### Strengths

- **~90 HTML demos** across 11 numbered top-level folders plus `d3_basics/` and `experiments/`. Each numbered folder is self-contained (its own HTML, optional README, inline static data).
- **Root-level navigator.** [`index.html`](../index.html) provides a searchable sidebar listing every demo with a description (generated by [`generateIndex.ps1`](../generateIndex.ps1)).
- **Consistent demo style.** [`dashboard/flowdash-demo.css`](../dashboard/flowdash-demo.css) gives demos a shared header / control bar / info footer look.
- **Theme showcase.** `01_basicNodes/03_states/themes-grid*.html` renders all 8 themes side-by-side.
- **Clear progression.** The numbering scheme (basic node → rectangular → circle → lane → columns → adapter → foundation → mart → group → edges → dashboard) is self-explanatory.
- **READMEs at meaningful boundaries.** Top-level READMEs in `04_laneNodes/`, `05_columnsNodes/`, `10_edges/`, `experiments/`.

### Gaps

- **Several core features have no dedicated demo.**
  - **Selection model** — single-click vs double-click neighborhood traversal (`settings.selector.incomming` / `outgoing`).
  - **Zoom** — programmatic, button-zoom, fit-to-viewport, auto-zoom-on-double-click.
  - **Status system** — the `NodeStatus` state machine, cascade behavior, auto-collapse-on-status (well-documented in [`dashboard/documentation/state.md`](../dashboard/documentation/state.md)).
  - **Minimap** — well-documented in [`dashboard/documentation/minimap.md`](../dashboard/documentation/minimap.md), never demonstrated visually.
  - **Overlay** — documented in [`dashboard/documentation/overlay.md`](../dashboard/documentation/overlay.md); only the `loading` overlay has a stub demo, and `11_dashboard/index.html` references a `01_loading/` folder that does not exist.
  - **Pre-render fast path** — no side-by-side cold-vs-prerendered demo despite the substantial pipeline at [`dashboard/prerender/`](../dashboard/prerender/).
- **No flagship dashboard showcase.** `11_dashboard/` is the right place for "all features composed" but contains only 2 files today (one of which references a missing folder).
- **Scratch / debug files in product folders.** `08_martNodes/debug_comparison.html`, `08_martNodes/debug_explicit_role.html` look like development leftovers.
- **Numbering inconsistencies.**
  - `d3_basics/` folder ids jump 03 → 10 → 11 → 12 → … with no 04-09.
  - `experiments/` uses 40–51 (`40_dwhflow/`, `41_dwhflow/`, `42_dwhflow/`, `50_network/`, `51_network/`) — disconnected from the main 01–11 scheme.
- **`experiments/` style drift.** Older inline styling, CDN imports for D3, no shared demo CSS — visually inconsistent with the rest of the demo set.
- **All demos use inline static data.** This is a deliberate choice (per project goal) but there is no example demonstrating the more realistic "load a JSON file" pattern that external consumers will use, even though `dashboard/data/` is full of suitable fixtures.
- **`dashboard/test-*.html` profiling pages** are scattered alongside the library (e.g. `test-performance.html`, `test-detailed-profiling.html`, `test-double-click.html`, `test-zone-system.html`) — they are real, useful tools but they are not surfaced in the navigator and overlap conceptually with `11_dashboard/`.

## Goal 3 — Comprehensive testing

### Strengths

- **Strong Playwright E2E foundation.** Root [`tests/`](../tests/) holds **19 spec files** covering all node types and major composed scenarios. The headline specs by size:

  | Spec                                  | Lines | Tests |
  | ------------------------------------- | ----- | ----- |
  | `columns-nodes-comprehensive.spec.js` | 1,100 | 26    |
  | `lane-nodes.spec.js`                  | 838   | 23    |
  | `lane-nodes-comprehensive.spec.js`    | 543   | 14    |
  | `groups.spec.js`                      | 462   | 22    |
  | `adapter-nodes.spec.js`               | 442   | 7     |
  | `rectangular-nodes.spec.js`           | 437   | 8     |
  | `integration.spec.js`                 | 376   | 16    |
  | `dashboard.spec.js`                   | 214   | 6     |
  | `foundation-nodes.spec.js`            | 210   | 7     |
  | `edges.spec.js`                       | 201   | 10    |

- **Cross-browser by default.** [`playwright.config.cjs`](../playwright.config.cjs) runs Chromium and WebKit projects; auto-starts `python -m http.server 8000` if not already running.
- **Failure artifacts captured.** `screenshot: 'only-on-failure'`, `video: 'retain-on-failure'`, `trace: 'on-first-retry'`.
- **Test data infrastructure.** [`tests/test-data-generator.js`](../tests/test-data-generator.js) extracts demo data into JSON; **20 fixtures** in [`dashboard/data/`](../dashboard/data/) including large-scale (`dwh-6.json` ~579 KB, `dwh-7.json` ~234 KB) and pre-render variants (`dwh-1.prerender.json`, `dwh-5.prerender.json`, `dwh-6.fixed.prerender.json`, `dwh-small.prerender.json`, `dwh-tiny.prerender.json`).
- **Documented strategy.** [`dashboard/tests/TESTING_STRATEGY.md`](../dashboard/tests/TESTING_STRATEGY.md) and [`tests/COMPREHENSIVE_TESTING.md`](../tests/COMPREHENSIVE_TESTING.md).
- **Performance instrumentation already exists.** The dashboard logs phase timings (dataLoad, nodeCreation, nodeInitialization, edgeCreation, layoutStabilization, zoomSetup, total) and node statistics (totalNodes, containerNodes, leafNodes, maxDepth) on every load — see [`dashboard/tests/PERFORMANCE_INSTRUMENTATION.md`](../dashboard/tests/PERFORMANCE_INSTRUMENTATION.md). Manual profiling harnesses live at `dashboard/test-performance.html`, `dashboard/test-detailed-profiling.html`, `dashboard/test-node-init-profiling.html`, etc.
- **Comprehensive runner.** [`tests/run-comprehensive-tests.js`](../tests/run-comprehensive-tests.js) orchestrates lane / column suites with retry logic and colored output. Exposed via `npm run test:comprehensive`.

### Gaps

- **No unit-test layer.** No Jest, no Vitest, no Mocha — neither root `package.json` nor `dashboard/package.json` lists a unit-test framework. Pure functions remain untested in isolation: `dashboard/js/utilPath.js`, `dashboard/js/geometryManager.js`, `dashboard/js/configManager.js` (settings deep-merge), `dashboard/js/forceBoundary.js`, `dashboard/js/forceRectCollide.js`, `dashboard/js/nodeRegistry.js`, status-machine transitions in `nodeBase.js`. The pyramid is currently inverted — every test is E2E.
- **No visual regression.** No `toHaveScreenshot()` baselines, no committed reference images, no snapshot diffs. Subtle rendering bugs (spacing, stroke, color shifts under theme changes) cannot be caught by current assertions.
- **No CI.** No `.github/workflows/` directory. Tests are local-only. `forbidOnly: !!process.env.CI` is set in the Playwright config but the env is never produced by an actual pipeline.
- **No coverage reporting.** No nyc, no c8, no istanbul config; coverage is untracked.
- **Performance instrumentation is not asserted.** The dashboard logs detailed metrics on every load, but no spec ratchets thresholds — a silent 3× regression would pass.
- **Hard-coded waits.** Specs call `waitForTimeout(250)` and `waitForTimeout(2000)` in places where readiness signals would be more reliable. Likely flakiness source.
- **Duplication / unclear ownership between two test directories.**
  - Root [`tests/`](../tests/) has 19 specs (the canonical suite, used by `npm test`).
  - [`dashboard/tests/`](../dashboard/tests/) has 2 specs (`zone-double-click.spec.js`, `debug-zone-creation.spec.js`) plus **8 manual profiling HTMLs and PowerShell wrappers** plus **3 strategy docs** (`PERFORMANCE_INSTRUMENTATION.md`, `RUN_TESTS_NOW.md`, `TESTING_STRATEGY.md`).
  - `zone-double-click.spec.js` exists in **both** locations — risk of divergence.
  - The `TESTING_STRATEGY.md` inside `dashboard/tests/` describes demo paths that no longer match the current `01_…` / `02_…` naming (it references `4_edges/`, `5_nodes/`, `6_groups/`, `7_dashboard/`). Likely stale.
- **Debug specs left in tree.** `tests/debug.spec.js`, `tests/debug-lane-test.spec.js`, `dashboard/tests/debug-zone-creation.spec.js` look exploratory rather than production tests.
- **Demo coverage by tests is patchy.** Specs heavily exercise `04_laneNodes/`, `05_columnsNodes/`, `06_adapterNodes/`, `07_foundationNodes/`, `08_martNodes/`, `10_edges/` and `dashboard/flowdash-js.html`. Not exercised: `01_basicNodes/02_layout-modes/` variants, `03_circleNodes/`, the `06_adapterNodes/` index navigator, theme variants, `09_groupNodes/`, the `dashboard/test-*.html` profiling harnesses.
- **Dashboard E2E is thin.** `dashboard.spec.js` has only 6 tests against `flowdash-js.html` — selection, zoom, theme swap, file-load are not deeply covered at the integrated dashboard level.

## Cross-cutting structural observations

- **`/docs/` was nearly empty** before this analysis (only `layout-properties.md`).
- **README references missing artifacts** (`TEST_PLAN.md`).
- **`todo.md` at repo root** is empty (1 line).
- **PowerShell-only scripts.** All distribution / index-generation / theme-injection scripts are `.ps1`. Fine on Windows; non-Windows contributors cannot run them.
- **Generated artifacts checked in.** `dashboard/dist/`, `dashboard/playwright-report/`, `dashboard/test-results/`, `dashboard/performance-results/` — worth deciding whether these belong in the repo or should be `.gitignore`d (left out of scope here).

## Summary

| Goal    | Status                                                                                                                                                                                                                                                                            |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Library | Strong: well-modularised, bundled, versioned, documented. Weak: dual-package versioning, missing release / contribution docs.                                                                                                                                                     |
| Demos   | Strong: many, organized, navigable. Weak: missing demos for several core features (selection, zoom, status, minimap, overlay, pre-render); no flagship showcase; scratch files in product folders.                                                                                |
| Testing | Strong: rich Playwright suite with cross-browser support and large-dataset fixtures; performance metrics already instrumented. Weak: no unit layer, no visual regression, no CI, no coverage, no asserted perf thresholds, two test-folder ownership confusion, hard-coded waits. |

See [`improvement-plan.md`](./improvement-plan.md) for the path forward.
