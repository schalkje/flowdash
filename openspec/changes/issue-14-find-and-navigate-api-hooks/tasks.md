## 1. Internal render-complete hook (foundational)

- [x] 1.1 Add a handler-registry on `Dashboard` (e.g. `this._eventHandlers = new Map()` keyed by event name, with `Set<handler>` values). Internal-only at this point.
- [x] 1.2 Add `_emit(eventName)` on `Dashboard`. Per D12 in design.md: (a) snapshot the handler set at emit start (`const handlers = [...(this._eventHandlers.get(eventName) ?? [])]`) so that handler mutations during emit affect only future emits; (b) iterate the snapshot in registration order, wrapping each invocation in `try { h(); } catch (err) { console.error('flowdash: render handler threw:', err); }` — `console.error` is intentional (not `_debugLog`) because handler errors are caller-code bugs that must surface in production.
- [x] 1.3 Wire `this._emit('render')` into `Dashboard.onMainDisplayChange`'s rAF callback **after** `_displayChangeScheduled = false` (i.e., immediately after `dashboard.js:2067`, not before it). Per D10a in design.md, the emit MUST happen after the flag is cleared so that re-entrant state mutations from handlers get their own fresh rAF rather than being coalesced into the in-flight pass. Add a one-line comment at the emit site noting that this is the public `render` event contract for issue #14, and that the post-clear ordering is intentional (re-entrancy safety).
- [x] 1.4 Wire a **guaranteed init-end emit**: add `this._emit('render')` at the end of `Dashboard.initialize()`, immediately after the `data-flowdash-ready="true"` attribute write (`dashboard.js:815`). This is required because `onMainDisplayChange` does not fire reliably during init for the default `zoomToRoot: false` non-prerender path (see D9 in design.md for the path matrix). The emit is direct (not routed through `onMainDisplayChange`) to bypass `_suspendDisplayChange` and rAF coalescing. Idempotency: handlers may receive two emits on the prerender path (one via `applyDeferredStatusRules` → `onMainDisplayChange`, one at init end) — the spec already requires handlers to tolerate this.
- [x] 1.5 Add `_hasEmittedSinceInit` state on `Dashboard` (initialize to `false` in the constructor). Set it to `true` inside `_emit('render')` so it covers all emit paths (prerender, init-end, per-flush). Used by `afterRender()` for idle-resolve detection per D10b.
- [x] 1.6 **Implementer note (future risk):** if `dashboard/js/simulation.js` (force-directed layout, currently inactive / out of scope) is reactivated, revisit whether per-tick `resizeBoundingContainer` cascades cause `render` to fire too frequently during a converging simulation. If yes, gate the per-flush emit on a "simulation is in flight" flag and emit additionally on `simulation.end`. No action required now — recorded so it shows up in code review when simulation comes back.

## 2. Public render-complete API (must-have)

- [x] 2.1 Add `Dashboard.prototype.on(eventName, handler)` and `Dashboard.prototype.off(eventName, handler)`. `eventName` MUST be `"render"`; other event names are ignored silently (a future expansion can add more event types without breaking this contract).
- [x] 2.2 Add `Dashboard.prototype.once(eventName, handler)` as a wrapper that registers a handler which removes itself before invoking the caller's handler.
- [x] 2.3 Add `Dashboard.prototype.afterRender()` with the D10b idle-resolve semantics: if `this._hasEmittedSinceInit && !this._displayChangeScheduled`, return `Promise.resolve()` (microtask resolve, no synthetic emit); otherwise return `new Promise(resolve => this.once('render', resolve))`.
- [x] 2.4 Add Playwright spec `tests/dashboard-render-event.spec.js` covering: (a) init-end guarantee — handler registered before `init` is invoked at least once before any state change, across all three paths (default non-prerender + `zoomToRoot: false`, non-prerender + `zoomToRoot: true`, prerender); (b) `afterRender()` resolves on a static dashboard post-init within one microtask AND does NOT invoke other `on('render')` handlers (no phantom emit); (c) `once` fires exactly once; (d) `off` by reference removes the listener; (e) per-flush coalescing — N `handleDisplayChange` bubbles within one frame produce exactly one emit; (f) re-entrancy — a handler that calls a mutating API (e.g., `setStatusToNodeById` or `addNode`) triggers a fresh rAF and a subsequent emit, not coalescing into the in-flight pass; (g) `afterRender()` called from inside a handler (without triggering state change) resolves in a microtask without invoking other handlers; (h) handler-throws — a throwing middle handler does NOT prevent earlier/later handlers from firing, the error is logged via `console.error` with `flowdash:` prefix, subsequent emits continue to invoke all handlers; (i) snapshot iteration — a handler that `on`s a new handler or `off`s a still-pending handler does not affect the current emit, only future emits; (j) handler survival across `setData` — a handler registered before `setData` is still invoked on the post-`setData` render emit. (Note: the prerender-path init-end scenario is exercised implicitly by the default-path and zoomToRoot-path tests sharing the same init-end emit code; a dedicated prerender-path test would require a fixture with pre-baked node positions, kept out of scope of this spec file.)
